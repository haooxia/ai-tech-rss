## 模型与多模态

### OpenAI 发布 GPT-6.1 Sol：把接近 Astra 的 Agent 能力下放到更低成本档
`Frontier Model` `Agent / Computer Use`

**更新：** OpenAI 于 9 月 29 日 DevDay 发布 GPT-6.1 Sol，官方定位为 GPT-6 Sol 的重大升级，重点提升 agentic coding、computer use 与专业工作，并称其提供接近 GPT-6 Astra 的能力、标准输入/输出 token 价格约为 Astra 的五分之一。API 模型页给出 **1,050,000 context / 128,000 max output**，标准价格为 **$2/M input、$0.10/M cached input、$10/M output**；支持文本与图像输入、function calling、computer use、MCP、web/file search 等工具。

**判断：** 它不是端侧候选，但很适合作为移动 Agent 的云端 teacher / evaluator / fallback：相比直接把最贵 frontier model 放在所有请求上，6.1 Sol 更适合承担复杂 tool routing、computer use 和长任务。对端侧路线的价值更多是建立“本地小模型做快速决策 + 云端强模型处理长尾复杂任务”的质量上限。

**来源：** [OpenAI / DevDay 2026 Recap](https://openai.com/index/devday-2026-recap/) · [OpenAI / GPT-6.1 Sol API](https://developers.openai.com/api/docs/models/gpt-6.1-sol)

## 音频、翻译与检索

### 非当日新闻｜近 7 天替换候选：NVIDIA Nemotron-3-Diarization 进入 100M 级本地说话人分离
`Speaker Diarization` `Local Speech`

**更新：** NVIDIA 于 **9 月 23 日**发布 Nemotron-3-Diarization，因此不算今日新闻；本次近 7 天候选扫描将其补入观察名单。模型为 **99.2M 参数**，支持 streaming / offline diarization、最多 8 个说话人，单 checkpoint 可配置到 0.32 s 推荐低延迟档；官方模型仓库已提供约 **107 MB 的 Q8_0 GGUF**，并可通过轻量原生 C++ runtime **NeMo-Speech.cpp** 本地运行和给 ASR 结果附加 speaker tag。

**判断：** 这比通用 LLM 更像真正适合会议/采访录音链路的端侧专用模型，尺寸也进入手机可研究区间。但 NVIDIA 官方验证仍以 Linux + NVIDIA GPU 为主，公开速度数据来自 RTX PRO 5000；目前没有 Android/ARM、LiteRT/MNN/QNN/HTP 的可运行或 full-delegation 证据，因此应视为**移植候选**，不能直接视为手机可部署方案。

**来源：** [NVIDIA / Nemotron-3-Diarization](https://huggingface.co/nvidia/Nemotron-3-Diarization) · [NVIDIA / NeMo-Speech.cpp](https://github.com/NVIDIA/NeMo-Speech.cpp)

## AI 行业热点

### OpenAI Decisions API：frontier 厂商正式进入“有限答案决策模型”接口
`Decision API` `Agent Routing`

**更新：** OpenAI 在 DevDay 推出 Decisions API，明确把 **Luna 的 intelligence 聚焦到用户定义的问题和有限预设答案**上；开发者可输入文本或图像上下文，返回结果用于分类、请求路由或选择 Agent 下一步动作。目前为 limited preview，官方称将在未来几天扩大开放。

**判断：** 这与你最近关注的 Jev / Ollaya / decision-model 路线高度相关：**“生成答案”与“在有限动作集合中做决策”正在被拆成独立产品层。** 但目前不能把 Decisions API 直接等同于 Jev：OpenAI 明确说它基于 Luna，尚未公开专用模型结构、calibration、延迟/价格或本地部署能力。真正值得追的是后续 API 形式、输出置信度、成本和 tool-routing 实测。

**来源：** [OpenAI / DevDay 2026 Recap — Decisions API](https://openai.com/index/devday-2026-recap/)

### OpenAI dots：手机变成长期 Agent 的控制面，执行留在独立云电脑
`Always-on Agent` `Cloud Runtime`

**更新：** OpenAI 发布 dots：由 **GPT-6 Astra** 驱动，每个 dot 拥有自己的 cloud computer，可 24/7 工作并连接 4,000+ apps；初始设置需桌面端/浏览器，之后可直接在 ChatGPT 手机 App 中消息交互。其后台 proactive research 对已连接 app 默认使用只读工具，Custom Rules 可配置 allow / require approval / block，影响账户或共享信息的动作还会经过 auto-review。

**判断：** 对移动 Agent 产品最值得看的并不是“模型放进手机”，而是其系统分层：**手机负责随时交互和审批，云端 worker 长期执行，权限/审查由模型外 runtime 管理。** 这和昨天 OpenShell 强调的 capability boundary 是同一趋势的另一种产品落地；对于真正需要低延迟、隐私或离线的动作，端侧小模型仍有独立价值。

**来源：** [OpenAI / Introducing dots](https://openai.com/index/introducing-dots/) · [OpenAI / DevDay 2026 Recap](https://openai.com/index/devday-2026-recap/)

## AI点评

1. **Decision model 正从小众路线变成正式 API 类型。** Jev、Ollaya 之后，OpenAI 直接把“有限答案决策”抽成 Decisions API；接下来最值得比较的不只是 accuracy，而是 latency、校准度、成本、结构化输出稳定性和是否能下沉到端侧。
2. **长期 Agent 的架构越来越清楚：模型、执行环境、权限层三者分离。** dots 的 cloud computer + Custom Rules/auto-review，与 OpenShell 的 runtime boundary 都说明高权限动作不能只依赖模型自己“守规矩”。
3. **语音链路值得继续寻找 100M 级专用模型，而不是所有能力都塞进大模型。** Nemotron-3-Diarization 这种 99.2M、可流式、本地 C++ 的 diarization 模型非常适合与你现有 ASR/TTS 组合；真正的门槛是 Android/ARM/NPU 移植和功耗，而不是模型尺寸。
4. **端侧 Runtime 今天仍处于“无新正式证据”的状态。** GenieX v0.7.1 的可观测性增强值得用，但在出现新的 graph partition、HTP artifact 或同机型实测之前，不应把版本活跃度误判为 NPU 性能突破。
