## SM8850 / LiteRT NPU 实测

### Matcha-TTS 补齐 Galaxy S26 / SM8850 Hexagon v81 实测：部分子图 NPU 明显快于 GPU，但 vocoder 仍无法编译
`#TTS` `#LiteRT` `#SM8850` `#Hexagon`

**更新：** LiteRT Community 在 Matcha-TTS 主模型卡加入 Galaxy S26（Snapdragon 8 Elite Gen 5 / SM8850、Hexagon v81、Android 16）的 NPU/GPU 对照。`matcha_textenc_fp16.tflite` 在 NPU 上为 7.15 ms，对比 GPU 10.69 ms，约快 1.49×；`matcha_decoder_fp16.tflite` 为 9.42 ms，对比 GPU 13.76 ms，约快 1.46×；G2P 子图在 GPU 上直接编译失败，而 NPU 可跑到 2.06 ms。另一方面，HiFi-GAN vocoder 的 SM8850 AOT 编译失败，因此当前还不能把整条 TTS pipeline 完整搬到 Hexagon。

**判断：** 这条对端侧 TTS 很有参考价值：SM8850 NPU 对 Transformer/CFM 主干已经有实际收益，但真正占 TTS wall time 的 vocoder 仍是瓶颈，所以不能只看 text encoder / decoder 的局部加速就判断整条链路已经适合 NPU。当前更现实的部署仍可能是 NPU + GPU/CPU 混合后端。

**来源：** [LiteRT Community：Matcha-TTS](https://huggingface.co/litert-community/Matcha-TTS)

### Zipformer CR-CTC：SM8850 全图 NPU delegation 后仍比 GPU 慢约 2.35～2.60×
`#ASR` `#LiteRT` `#SM8850` `#NPU`

**更新：** Zipformer CR-CTC small / medium / large 三个 LiteRT 模型新增 Galaxy S26 / SM8850 实测。三者重新为 SM8850 编译后都实现完整单分区 NPU 执行，并非部分回退：small 2342 ops、medium 3085 ops、large 3637 ops 全部进入 Hexagon。但推理延迟分别为 NPU 70.88 / 84.59 / 118.7 ms，而 Adreno GPU 为 28.86 / 35.96 / 45.61 ms；也就是 GPU 仍快约 2.46× / 2.35× / 2.60×。NPU 的优势主要在加载时间，约 355～615 ms，对比 GPU 2.0～3.1 s。

**判断：** 这是今天最值得记住的负向 benchmark：**full NPU delegation 不等于 NPU 更快。** 对 ASR encoder 这类图，SM8850 上 GPU 仍可能明显占优。以后评估 QNN/HTP/LiteRT NPU 路线，必须把“是否全图下沉”和“实际端到端 latency/功耗”分成两个独立指标。

**来源：** [LiteRT Community：Zipformer-medium-CR-CTC-LiteRT](https://huggingface.co/litert-community/Zipformer-medium-CR-CTC-LiteRT)

### DINOv2 ViT-S/14：仅改 GELU 表达方式，SM8850 NPU 从落后 GPU 变成领先
`#Vision` `#FeatureExtraction` `#LiteRT` `#SM8850`

**更新：** DINOv2 ViT-S/14 的 SM8850 NPU 测试给出了一个非常典型的图优化案例。原始 `dinov2_s_fp16.tflite` 使用 tanh-GELU 分解，NPU 延迟 85.9 ms，慢于 GPU 的 54.7 ms；将同一模型的 MLP GELU 改为 LiteRT builtin GELU（exact erf）后，`dinov2_s_erf_fp16.tflite` 的 NPU 延迟降到 41.9 ms，而 GPU 为 55.2 ms。两版特征相关性 0.99999，说明差异来自图表达/编译器 fast path，而不是模型本身改变。

**判断：** 这条对图像检索/相册视觉特征尤其重要：模型结构相同，单纯 operator re-authoring 就能让 SM8850 NPU 从“比 GPU 慢”翻转为“比 GPU 快”。端侧模型转换不能只做机械 ONNX/TFLite 导出；针对 Hexagon/QNN/LiteRT compiler 的算子表达优化，可能比换量化策略还关键。该模型仅约 45 MB、输出 1024×384 patch tokens，也很适合作为轻量视觉特征 backbone 的部署参考。

**来源：** [LiteRT Community：DINOv2-ViT-S14-LiteRT](https://huggingface.co/litert-community/DINOv2-ViT-S14-LiteRT)

## 小模型与文档 AI

### Granite Docling 258M 新增 LiteRT-LM 包：338 MB 的端侧结构化文档解析 VLM
`#VLM` `#OCR` `#DocumentAI` `#LiteRT-LM`

**更新：** LiteRT Community 新发布 `granite-docling-258M` 的 LiteRT-LM 转换，用于把页面图片直接转换成 DocTags，再无损转 Markdown / HTML / JSON。模型只有 258M 参数，LiteRT-LM 包约 338 MB；视觉侧为 SigLIP-base 512×512，经 pixel-shuffle + connector 压成 64 个 image tokens，decoder 为 30 层 Granite/Llama 架构。Galaxy S26 / SM8850 CPU 上，官方社区实测一张 5×6 表格测试页可完整恢复标题、表格结构和 25/25 个数据单元，约 35.4 s/page；Google AI Edge Gallery 1.0.18 中同页约 34.7 s。

**限制：** 输入必须由 App 侧先以 BILINEAR 精确 resize 到 512×512；不同 resize filter 会导致严重退化。INT4 已测试但会破坏 DocTags，因此当前使用 INT8 weights + float compute；已发布 bundle 的 GPU engine 会因量化 projection shape mismatch 创建失败，FP16 decoder 虽能跑 Android OpenCL，但约比 CPU 慢 4×，因此当前明确以 CPU 为目标后端。

**判断：** 这是一个很有意思的“真正小型文档 VLM”：尺寸已经进入移动端可接受区间，并且不是单纯 OCR，而是直接输出表格/布局结构。不过 Galaxy S26 上单页 35 秒仍偏慢，且 512² 单视图对密集小字/公式有限制。现阶段更适合离线扫描、票据/简单表格等非实时场景，而不是实时相机文档理解。

**来源：** [LiteRT Community：granite-docling-258M](https://huggingface.co/litert-community/granite-docling-258M)

## AI点评

- **今天最重要的不是“SM8850 NPU 很快”，而是它越来越像一个需要针对图结构逐模型调优的后端。** Matcha-TTS 部分图 NPU 胜出、Zipformer 全图 NPU 却明显输给 GPU、DINOv2 只改一个 GELU 表达就完成性能翻转，这三组结果比单一峰值数字更有价值。
- **以后看 NPU 适配至少拆成四层：** 能否编译 → 是否 full delegation → 数值/输出是否正确 → 实际 latency、内存、功耗是否胜出。前三项过了，也不保证第四项成立。
- **对相册/视觉检索方向，DINOv2 这条尤其值得借鉴。** 相同权重、相同语义质量，operator rewrite 就把 NPU latency 从 85.9 ms 拉到 41.9 ms；这说明转换工具链里应当有“面向目标 SoC 的图重写/fast-path 优化”阶段，而不是只做格式转换。
- **Granite Docling 258M 证明专用小 VLM 仍有很强的端侧价值。** 与其把 2B～4B 通用 VLM 硬塞进手机，258M 这种针对文档结构化任务的小模型更接近可落地路线；当前主要瓶颈已经从 ROM 转向速度和输入分辨率。
