## 端侧框架与运行时

### LiteRT 修正 `CompiledModel` 的非 CPU 全量 delegation 判断
`#LiteRT` `#NPU部署`

**更新：** LiteRT 在 8 月 17 日凌晨合入一项 `CompiledModel` 修复：判断“是否完全由非 CPU 加速器接管”时，不再用 `GPU delegated nodes + NPU delegated nodes == total nodes`，而是直接要求 CPU delegated node 为 0 且当前 undelegated node 为 0；当调用方没有允许 CPU 时，编译失败条件也改为直接检查是否仍存在 undelegated nodes。

**判断：** 这不是新增某款手机 NPU backend，但对 NPU/GPU 部署的正确性很重要。旧逻辑把“非 CPU 加速”近似成 GPU+NPU 计数，可能在存在其他 accelerator/dispatch 路径或统计口径差异时误判；新逻辑更接近真正需要确认的问题——是否还有节点落在 CPU 或根本没有被 delegate。对实际手机 NPU 验证来说，这能减少“明明已完整加速却被判失败”或依赖错误统计口径的风险。不过它并没有新增 Snapdragon、MediaTek、Google Tensor 或 Exynos 的 NPU 算子/模型覆盖，因此不能解读成新的手机 NPU 支持。

**来源：** [LiteRT commit](https://github.com/google-ai-edge/LiteRT/commit/72f9a4e9032fabdc659ad30bdf0a496455bfed82)

## AI点评

- 今天最值得注意的不是“又多支持了一个 NPU”，而是 LiteRT 开始把“是否真正完全 delegation”判断得更直接。对手机 NPU 工程来说，准确识别 fallback 本身就是基础设施能力。
- 过去几天 LiteRT 已陆续补上 per-accelerator delegation/partition 统计，而今天又修正 `CompiledModel` 的 full-delegation 判定；两者连起来看，LiteRT 对加速器可观测性正在明显变好。
- 业务模型扫描仍应坚持“质量 + 体积 + 真机 runtime/NPU”三项一起看。Falcon-H1 1.5B 这种新转换值得试，但没有 NPU 实测、GPU 内存偏高时，不应因为参数小就直接视为升级。
