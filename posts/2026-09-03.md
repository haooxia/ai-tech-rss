## 端侧框架与运行时

### Sarashina2.2 0.5B / 1B 新增 LiteRT-LM：Galaxy S26 GPU 全图运行
`LiteRT-LM` `Small LLM`

**更新：** LiteRT Community 在本窗口新发布日语优先的 `sarashina2.2-0.5b-instruct-v0.1` 与 `sarashina2.2-1b-instruct-v0.1` LiteRT-LM 包，均为 MIT License。0.5B 版本提供 871 MB int8 / 534 MB int4；Galaxy S26 上 int8 GPU prefill 862–895 tok/s、decode 36.2–36.5 tok/s、峰值 RSS 849 MB。1B 版本提供 1.505 GB int8 / 904 MB int4；Galaxy S26 上 int4 GPU decode 27.4–27.5 tok/s。两款模型的全部 prefill signature 与 decode 图均实现 OpenCL 全图 delegation、无 XNNPack fallback，并专门做了 tokenizer、emoji/异体字和多轮对话一致性检查。

**判断：** 这是一组很具体的 0.5B–1B 手机小模型部署样本，尤其说明大词表模型里 int4 未必总比 int8 快；但当前是 **Adreno/OpenCL GPU**，不是 QNN/HTP NPU。模型以日语为主，对中文业务更适合作为 LiteRT-LM 小模型性能/转换参考，而不是直接替换候选。

**来源：** [LiteRT Community / sarashina2.2-0.5b-instruct-v0.1](https://huggingface.co/litert-community/sarashina2.2-0.5b-instruct-v0.1) · [sarashina2.2-1b-instruct-v0.1](https://huggingface.co/litert-community/sarashina2.2-1b-instruct-v0.1)

### Microsoft 发布 VibeVoice-ASR-Streaming 1.5B / 7B：实时“谁说了什么”+ 热词
`ASR` `Streaming`

**更新：** Microsoft Research 新发布 `VibeVoice-ASR-Streaming-1.5B` 与 `VibeVoice-ASR-Streaming-7B`，把此前长音频 batch ASR 扩展为真正按 chunk 连续输出的流式版本。官方 7B 模型卡明确支持 speaker-attributed transcription、custom hotwords，以及中文、英文、法文、德文、意大利文、日文、韩文、葡萄牙文、俄文、西班牙文 10 种语言，采用 MIT License；vLLM 部署文档提供 WebSocket / REST，并通过 prefix-cached session 复用前序 chunk 的 KV cache。

**判断：** 对实时通话/会议 ASR 很值得跟踪，尤其是“流式 + speaker attribution + hotword”组合；但当前官方部署路径以 CUDA / vLLM 为主，7B 页面实际标注约 9B params，也没有 LiteRT / MNN / QNN / HTP 手机路径或公开真机延迟，因此现阶段不是端侧替换模型。

## AI点评

1. **今天端侧最值得看的其实是两类“基础设施能力”：Sarashina 的完整手机 GPU 路径，以及 Gallery 1.0.19 的 App 集成能力。** 前者说明模型本身如何跑，后者解决模型资源、会话和多 SoC 分发，两者缺一不可。
2. **继续严格区分“设备专用 APK”与“NPU 支持”。** Gallery 已经直接发 SM8850 APK，但这不是 Hexagon/QNN benchmark；只有具体模型编译、full delegation、正确性和真机性能都核验后，才能说 NPU 路径成熟。
3. **VibeVoice-ASR-Streaming 的方向比模型尺寸更值得关注。** prefix-cached session 把 ASR 从一次性 batch 变成持续状态机；如果未来能蒸馏到 0.5B–1B 并进入 LiteRT/QNN，这种“流式 + speaker attribution + hotword”非常贴近实时翻译产品。
4. **Agent 模型的效率指标正在从 tok/s 转向“完成任务用了多少轮”。** Gemini 3.8 Flash 与 Muse Spark 1.3 都在长程 Agent/Coding 上发力；对端侧评估也应逐步增加 tool calls、累计 tokens、重复 prefill 和任务完成率，而不只看单轮生成速度。
