## 端侧框架与运行时

### LiteRT Community 批量修复 LiteRT-LM tokenizer：多款 VLM/LLM 的非 ASCII、emoji 与特殊 token 输入此前可能被错误编码
`#LiteRT-LM` `#Tokenizer` `#VLM` `#Multilingual`

**更新：** LiteRT Community 在过去约 13 小时集中替换了一批 `.litertlm` bundle 的 tokenizer section。受影响的公开模型包括 InternVL3 / InternVL3.5、LLaVA-OneVision-0.5B、Mage-VL、SmolVLM2、SmolLM3-3B、Qwen2-VL-2B、Ovis2.5-2B 等。多数问题来自把原始 byte-level BPE 转成 SentencePiece 后丢失 byte semantics：`é`、`ñ`、`ü`、`°`、`·` 等字符可能被编码成错误 id；emoji 和大量 Latin Extended-A 字符甚至可能落到被复用为 UNK / end-of-text 的 token。现在相关 bundle 改为直接嵌入上游 `tokenizer.json`。

**验证：** 模型卡明确说明这次只替换 tokenizer，weights、graph 和 chat template 均保持 byte-identical；LiteRT-LM runtime 已用默认对话、7 组 probe、U+00A1～U+017F 的 223 个独立字符及全部 special token 对齐上游 tokenizer。ASCII-only 测试问题的输入 token 和输出保持一致，但包含重音字符、符号或 emoji 的 prompt 现在会以正确 token stream 到达模型。

**一个很严重的例子：** `SmolLM3-3B.litertlm` 的旧转换甚至把 `<|im_end|>` 变成 6 个拼写出来的 token，而 emoji 会被当成 end-of-turn；8 月 30 日的新 bundle 已修复。PaddleOCR-VL-1.6 属于另一类 tokenizer bug：原 SentencePiece 中部分 special token 被标成 CONTROL，导致 chat template 里的 `</s>` 无法作为单个 special token 匹配；新 bundle 将这些 piece 改成可匹配的 USER_DEFINED，同时保持 id 不变。

**判断：** 这不是“页面刷新”，而是会改变真实输入 token stream 的部署级正确性修复。对中文主流程影响未必最大，但对多语言文本、emoji、OCR/VLM 中的特殊符号、摄氏度/数学符号以及多轮对话边界非常关键。已经下载过这些 LiteRT-LM bundle 的业务应重新下载 2026-08-30 版本；旧 benchmark 的每-token 性能仍可参考，因为权重与计算图未变，但涉及非 ASCII prompt 的质量结果不应继续沿用旧包。

## Voice Agent / 模型优化

### Pipecat 新发布 PhoneLLM Alpha 1 NVFP4：Blackwell 专用量化，PhoneBench 几乎无损
`#VoiceAgent` `#NVFP4` `#MoE` `#Pipecat`

**更新：** Pipecat 在过去约 3 小时新发布 `phonellm-alpha-1-nvfp4`，是 PhoneLLM Alpha 1 的官方 NVFP4 量化版，面向 NVIDIA Blackwell 原生 NVFP4 执行。模型基于 Nemotron 3 Nano 架构，30B 总参数、3.5B 激活，采用 selective NVFP4 weight quantization、group size 16；artifact 为 52 个 safetensor shard、约 19.4 GB，官方在单张 B200 + vLLM 0.27.1 上验证。

**质量：** 官方对 PhoneBench 做 10 次完整运行：BF16 + BF16 KV 为 72.0558；NVFP4 + BF16 KV 为 72.0191，仅下降 **0.0367**；NVFP4 + FP8 KV 为 71.5125，下降 0.5433。官方因此推荐 NVFP4 weights + BF16 KV；代价是相比 FP8 KV，可用 KV-token capacity 约少 40.2%。

**背景与判断：** 原始 PhoneLLM Alpha 1 是针对电话 Voice Agent 的全参数 SFT，重点优化低延迟、多轮对话和 tool calling。Pipecat 报告其在 PhoneBench 上可达到与 GPT-5.6 Terra 相近的表现，同时其自托管方案成本低约 94%、P95 TTFT 快约 1.3 秒。今天真正的新变化是 **NVFP4 量化版本发布**，而不是把前两天的 BF16 模型重新算新闻。它显然不是手机端模型，但对服务端实时翻译/语音 Agent 的低延迟 LLM 选型值得记录；如果以后出现 3B～7B 级同类专用模型，才更可能进入移动端候选范围。

**来源：** [Pipecat Hugging Face Activity](https://huggingface.co/pipecat-ai) · [PhoneLLM Alpha 1 NVFP4](https://huggingface.co/pipecat-ai/phonellm-alpha-1-nvfp4) · [PhoneLLM Alpha 1](https://huggingface.co/pipecat-ai/phonellm-alpha-1)

## AI点评

- **今天最值得注意的是“模型包的 tokenizer 也是部署资产的一部分”。** 权重和计算图完全没变，但 token stream 错了，模型照样会产生系统性质量问题。对端侧多模态模型，验收不能止于模型输出和性能 benchmark，应该把 tokenizer/chat template/special token 做成独立的一致性测试。
- **建议把 tokenizer parity 纳入端侧转换 CI：** 至少覆盖中英文、重音拉丁字符、emoji、数学/单位符号、全部 special tokens、多轮 chat template，并逐 token 对比 Hugging Face upstream。今天 LiteRT Community 用 U+00A1～U+017F 全覆盖 probe 的方式很值得直接借鉴。
- **PhoneLLM 的价值不在“30B 也能上端侧”，而在专用小激活 MoE + 场景化 SFT + 硬件原生低比特量化。** 3.5B active 的模型通过 NVFP4 几乎保持 PhoneBench 质量，说明实时 voice agent 的效率路线越来越依赖“任务专用模型 + serving/quantization 联合优化”，而不是单纯追求通用大模型能力。
- **继续严控时间真实性。** 今天 Hugging Face 出现大量“Updated hours ago”的模型，但其中不少只是卡片/metadata/bundle 修复；只有能证明实际改变了部署行为的 tokenizer 更新被纳入正文，旧 benchmark、新爬取结果和重复报道全部排除。
