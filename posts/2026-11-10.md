### Google 发布 TPU 8tx 与 TPU 8i Max：面向机密推理和超长上下文 Agent

**标签：** AI Hardware · Agent Infrastructure

**更新：** Google **11月9日**宣布第八代 TPU 两个新系统：**TPU 8tx** 以 TPU 8t 配合 AMD EPYC 主机和硬件机密计算，面向敏感模型与数据，Google 声称比 TPU 8t 延迟最高降低约2倍；**TPU 8i Max** 将两个 TPU 8i 芯片封装在一起，使计算能力、SRAM 与 HBM 带宽较单 TPU 8i 翻倍，针对大上下文和多 Agent 工作负载。两者是数据中心 TPU **系统配置**，并非新手机 NPU。

**判断：** 新增的 TPU Sync（分层管理 KV / 模型状态）、Agent Compute Engine（空闲会话挂起）、TorchTPU 及 TPU Agent Suite 体现 Agent 基础设施开始优化持续会话、上下文和运维。Google 宣称 TPU Sync 能将部分 KV 传输延迟和 TTFT 降低90%以上，但这是其特定云端场景的官方数据，不能外推到手机。对端云混合 Agent 的参考价值高于对 Snapdragon HTP 直接替换价值。

### Amazon HOPE：利用专家协同关系剪枝 MoE，减少推理权重占用

**标签：** MoE Pruning · Optimization

**更新：** Amazon/AWS 研究人员 **11月9日**在 Hugging Face 发布 HOPE（Higher-Order Pruning of Experts）技术文章与可运行三步工具链：校准、求解二次优化、剪枝。它保留专家之间的成对协同关系，而非仅按单专家重要性裁剪。研究论文原始时间为 **2026年9月**，因此本期新增的是官方工程解读/实现推广，**不是11月9日首发论文**。研究方报告，在 Qwen3.5-35B-A3B 的50%专家剪枝设置中，SWE-Bench Pro 为 **42.3**，对比未剪枝 **41.8**、REAP 剪枝 **36.2**；属于研究方特定测试条件，不能视为普遍提升。

**判断：** 这条对端侧模型压缩有方法论价值：MoE 总参数决定常驻内存，专家剪枝可与量化叠加。但验证对象主要是35B/122B等大 MoE，并非已交付的0.1B–4B Android 模型；尚无 SM8750 HTP 兼容、峰值内存、速度或功耗证据。可作为大 MoE 蒸馏/剪枝探索，不宜直接取代 Needle3。

**来源：** https://huggingface.co/blog/amazon/higher-order-pruning-experts · https://github.com/awslabs/HOPE · https://arxiv.org/abs/2609.18916

5. **GenieX 仍以正式 tag 与真机数据为准。** 后续重点追踪 MTP KV 一致性、HTP session、SM8750/SM8845 的 graph partition 和持续功耗，而不是重复旧 PR。
