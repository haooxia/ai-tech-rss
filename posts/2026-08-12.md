## 端侧框架与运行时

### LiteRT / LiteRT-LM

#### LiteRT-LM v0.16.0 正式发布：首次提供版本化 C API 预编译包

`LiteRT-LM` `Release`

**更新：** LiteRT-LM 在本统计窗口内正式发布 **v0.16.0**。核心变化包括首次为支持平台提供版本化 C API shared-library prebuilts，降低原生应用和其他语言 binding 的集成门槛；同时加入实验性 **YNNPACK delegate**，当前在 Linux arm64 的 LiteRT-LM CLI 与 Python API 中启用。

**意义：** 这次变化不是普通仓库提交，而是正式 Release。C API 预编译包对 Android/iOS/原生端集成的长期价值很高：应用侧不必每次自己处理完整共享库构建链路，LiteRT-LM 正在从“模型运行框架”继续向可嵌入 runtime 演进。YNNPACK 则值得关注其后续是否扩展到更多移动平台与低比特模型路径。

**端侧判断：** C API prebuilts 已经是现实可用的集成能力；YNNPACK 目前仍明确标注为 experimental，而且本次 Release 只说明 Linux arm64 的 CLI/Python 路径，不应描述为 Android 已默认支持。

**来源：** [LiteRT-LM v0.16.0 官方 Release](https://github.com/google-ai-edge/LiteRT-LM/releases/tag/v0.16.0)

#### v0.16 发布后主干继续推进 NPU 与 Embedding 能力（普通 commit，非 v0.17 Release）

`LiteRT-LM` `NPU`

**更新：** v0.16.0 之后，LiteRT-LM 主干已经将版本号 bump 到 0.17.0 开发阶段，但目前不能把它视为 v0.17 正式发布。同一窗口内还合入了 NPU warmup 后 buffer 清理/辅助 buffer 初始化，以及 EmbeddingEngine 的 metadata、BOS/EOS、vision preprocessing 等改动。

**意义：** 这些提交同时指向两个值得继续追踪的方向：一是 NPU backend 的生命周期与内存管理继续收敛，二是 EmbeddingEngine 正在补齐视觉与特殊 token 元数据能力，对端侧 embedding / 图文检索链路有潜在价值。

**端侧判断：** 目前属于主干开发进展，适合用于判断下一版方向，不应当成稳定 Release 能力。尤其是 NPU buffer 改动，需要后续 Release notes 或实机回归才能判断是否会解决具体加载/内存问题。

**来源：** [NPU buffer 提交](https://github.com/google-ai-edge/LiteRT-LM/commit/e3feda9ea47ef5c111e8edbe5f80c28f7f5a2e17) · [Embedding metadata 提交](https://github.com/google-ai-edge/LiteRT-LM/commit/a6f7effa3506cdef175a8def7008ee8b6b961ec3) · [Vision preprocessing 提交](https://github.com/google-ai-edge/LiteRT-LM/commit/4d27740e0be2063fa28cfc94b4134b777c213780)

### MNN

#### DFlash 复用目标模型 LM Head：Qwen3-4B Int4 可减少约 219 MB 重复权重

`MNN` `内存优化`

**更新：** MNN 调整 DFlash speculative decoding：draft 不再单独携带与 target 相同的 `lm_head`，而是直接复用目标模型的 LM Head。官方提交以 Qwen3-4B Int4 为例，指出可减少约 **219 MB** 的磁盘与运行时重复权重；M5 iPad 上的 2B Int4 测试中 acceptance 基本保持不变。

**意义：** 这是非常典型、也很实用的端侧优化。相比几个百分点的 kernel 提速，直接减少数百 MB 重复权重会更明显地改善手机/平板上的 ROM、RAM 与 speculative decoding 可部署性。

**端侧判断：** 已有 iPad 实测，不只是理论内存估算；但该提交改变了 DFlash 导出/加载约定，旧 draft 需要按新格式重新导出，升级时应关注兼容性。

**来源：** [MNN 官方 Commit](https://github.com/alibaba/MNN/commit/bc85588f29e42b521dcff8a7a573c6423d7e09ad)

#### MNN 新增 Qwen3-TTS-12Hz-0.6B-Base 支持

`MNN` `TTS`

**更新：** MNN 主分支合入对 **Qwen3-TTS-12Hz-0.6B-Base** 的支持。这是 MNN 的普通 feature commit，不是新的 MNN Release，也不是 Qwen3-TTS 模型本身今天新发布。

**意义：** Qwen3-TTS 0.6B 级模型本身具备明显的端侧探索价值；MNN 开始直接适配，意味着它从“理论上可以压缩后上设备”进一步进入真实移动 runtime 的工程路径。

**端侧判断：** 目前能确认的是 MNN runtime 支持已经落到主干，尚不能据此推断 Android 上的 ROM/RAM、RTF、首包延迟或 NPU 可用性。下一步最值得看的是量化方案和手机实测。

**来源：** [MNN 官方 Commit](https://github.com/alibaba/MNN/commit/becf43ef3d207206a6883c9dfca380c347defc95)

#### MNN 修复 QNN 多模态导出目录组织问题

`MNN` `QNN`

**更新：** MNN 合入 QNN bugfix，使 LLM 与 visual MNN 模型能够转换到同一个 QNN 输出目录，解决多组件模型转换时的产物组织问题。

**意义：** 这类修复看起来不如新算子显眼，但与真实多模态 Android/QNN 工程链路更接近。对语言模型 + vision encoder/projector 组合而言，更统一的 QNN 产物目录可以减少部署侧额外搬运与路径处理。

**端侧判断：** 属于明确的部署链路 bugfix，但仍是主干 commit；建议等进入正式版本后再作为稳定能力依赖。

**来源：** [MNN 官方 Commit](https://github.com/alibaba/MNN/commit/e24ef7c0acef2ffb02fbda452360b3a9197a855d)

**来源：** [llama.cpp b10375 官方 Release](https://github.com/ggml-org/llama.cpp/releases/tag/b10375)

#### llama.cpp Vulkan 首次加入 TQ2_0 ternary 支持

`llama.cpp` `低比特量化`

**更新：** llama.cpp 主分支为 Vulkan backend 加入 **TQ2_0 ternary** 支持，包括 dequant、`mul_mat_vec`、matmul 与 `get_rows` 等路径。提交说明在 OM-125m 测试中，TQ2_0 与 F16 的 top-12 logprobs 可对齐到 4 位小数；125M 规模上速度约等于 F16，作者明确指出更大的 BitNet/ternary 模型才更可能体现带宽收益。

**意义：** 这是低比特模型从“有 GGUF 格式”走向 GPU backend 真正可执行的重要一步。Vulkan 覆盖 Android GPU，因此对后续 ternary / BitNet 类小模型的移动 GPU 部署具有现实意义。

**端侧判断：** 已有 Vulkan backend 实现，但当前提交没有 Android 手机 benchmark，也没有证明在 Adreno 上一定快于 4-bit；现阶段应视为“runtime 已具备基础支持”，而不是“手机性能已经验证”。

**来源：** [llama.cpp 官方 Commit](https://github.com/ggml-org/llama.cpp/commit/a7cd2f0e98ffa4e939276287be1fa76891908d2e)

#### llama.cpp 针对 X1E 调整 OpenCL FlashAttention 参数

`llama.cpp` `Adreno`

**更新：** llama.cpp 的 OpenCL backend 将 X1E 平台 FlashAttention c8 的默认 cluster width 调整为 16。这是设备定向优化 commit，并非单独 Release。

**意义：** 它说明 Qualcomm/Adreno 路线仍在持续做硬件特定 tuning。对于 Snapdragon / X Elite 一类设备，比通用 CUDA 优化更值得跟踪。

**端侧判断：** 当前提交摘要没有给出可复用的手机端性能数字，因此更适合作为后续 benchmark 观察点，而不是直接宣称获得固定百分比加速。

**来源：** [llama.cpp 官方 Commit](https://github.com/ggml-org/llama.cpp/commit/89e0aa6fd362617d9073e0dafc18e41241521572)

## 小模型 / 手机可部署模型

#### LiteRT Community 上线 Bonsai Image ternary 4B：完整 Text-to-Image pipeline 可在手机本地运行

`LiteRT` `Text-to-Image`

**更新：** LiteRT Community 在本窗口内发布 **Bonsai-Image-ternary-4B** 的 LiteRT 转换版本，用三个固定 shape 的 `.tflite` 图完成完整 text-to-image pipeline。最小组合中，DiT 为 int4 block-32、约 **2.11 GiB**；裁剪后的 Qwen3-4B text encoder 为 int4、约 **1.68 GiB**；VAE 约 **0.19 GiB**，最小工作集文件总量约 **3.97 GiB**。

模型卡给出了实际设备数据：iPhone 17 Pro 使用 CPU/XNNPACK 生成一张 512×512 图片约 **64 秒**、峰值内存约 **2.9 GiB**；Pixel 8a（8 GB RAM）约 **7–8 分钟**。模型卡建议把 8 GB RAM 视为下限、Android 12 GB+ 作为更现实的目标，并提供 Android / iOS 示例应用。

**意义：** 这次值得关注的不只是“4B 模型可以量化塞进手机”，而是 **LiteRT 已经有完整转换产物、运行脚本、Android/iOS demo 和真机数据**。端侧生成模型的范围正在从 LLM/VLM 扩展到 text-to-image。

**端侧判断：** 这是“已有实际移动端 runtime 适配”，不是纯理论判断。不过 Android CPU 性能目前仍明显偏慢，且 3–4 GiB 级模型文件/工作集对内存和存储要求较高；现阶段更像高端手机技术验证，而非普适实时体验。需要注意，该模型位于 **LiteRT Community**，属于社区转换，不等同于 Google 官方基础模型发布。

**来源：** [Hugging Face · litert-community/Bonsai-Image-ternary-4B](https://huggingface.co/litert-community/Bonsai-Image-ternary-4B)

## AI点评

- **LiteRT-LM v0.16.0 是今天最应该补上的漏项。** C API prebuilts 比普通 API 改名更接近“框架真正可嵌入应用”的成熟度提升；而主干已经进入 0.17 开发，但目前绝不能把版本 bump 当成正式发布。
- **端侧生成正在从文本走向图像。** Bonsai Image 4B 已经给出 LiteRT、Android/iOS demo 和真机数据；问题从“能不能跑”开始变成“内存、热量和分钟/秒级延迟能否接受”。
- **内存优化的重要性正在超过小幅算力优化。** MNN DFlash 直接复用 LM Head、单项减少约 219 MB，对 2B–4B 级端侧模型比很多几个百分点的 kernel 提速更有工程价值。
- **低比特格式只有被 backend 真正执行才有意义。** llama.cpp 为 Vulkan 加入 TQ2_0 是个值得持续观察的节点；下一步关键不是更多 GGUF 文件，而是 Adreno / Mali 真机吞吐和功耗数据。
- 接下来最值得追踪的是 **LiteRT-LM 0.17 的 NPU/Embedding 改动何时进入正式 Release、MNN 的 Qwen3-TTS 是否出现 Android 实测、以及 ternary 模型在移动 GPU/NPU 上能否从“省内存”进一步变成“也更快”。**
