### LiteRT / LiteRT-LM

#### LiteRT 将 Android minSdkVersion 提升到 24

`LiteRT` `Android`

**更新：** LiteRT 主分支在本统计窗口末段将 Android `minSdkVersion` 提升到 **24**。这是普通 commit，尚不是新的正式 Release；当前 latest Release 仍为 v2.1.6。

**意义：** 这是直接影响 Android 集成边界的兼容性变化。后续若该变更进入正式版本，应用最低系统要求将至少来到 Android 7.0 / API 24；仍需兼容更老 Android 的项目应在升级时重点检查依赖版本和构建配置。

**端侧判断：** 这是源码主分支已经发生的真实兼容性变化，但正式发布前不应描述为“当前稳定版已要求 API 24”。建议重点观察下一次 LiteRT Release 是否正式携带该门槛。

**来源：** [LiteRT 官方 commit](https://github.com/google-ai-edge/LiteRT/commit/1cdcf087ab05e632ac48e7f4f189c960e931cb4f)

#### LiteRT 补强 Int2 / Int4 转换与硬件加速可观测性

`LiteRT` `量化 / 模型优化`

**更新：** LiteRT 主分支的一组提交继续补低比特和加速器能力：IR 转换路径将 Embedding Lookup 提升到支持 **Int2 / Int4** 的版本，并增加 Int4 Cast 支持；同时 runtime C API / C++ Environment 增加 accelerator query API，并暴露“compiled model 是否完全由非 CPU 加速”的查询能力。XNNPACK 路径也新增对动态量化 FullyConnected 的 FP16 支持。

**意义：** 这组变化同时解决两个端侧问题：一是让低比特模型更容易通过转换链路，二是让应用能够程序化确认模型是否真正落到硬件加速器，而不是仅凭配置推测。对 NPU / GPU 部署排障尤其有价值。

**端侧判断：** 目前均为主分支普通提交，不代表所有 Int2 / Int4 模型已经可在所有 Android 加速器上运行；真正可用性仍取决于算子覆盖、目标 delegate/backend 和 SoC 支持。

**来源：** [Int2 / Int4 转换修复](https://github.com/google-ai-edge/LiteRT/commit/f90a15b6f9753d241672190a36dafd2996c61425) · [Accelerator query API](https://github.com/google-ai-edge/LiteRT/commit/4c725b652715f0e5f463d01757245ae25ba5a722) · [非 CPU 全加速查询](https://github.com/google-ai-edge/LiteRT/commit/edfd0f5ee454e62edb66685c4e669dfd83b5002f) · [XNNPACK 动态量化 FC FP16](https://github.com/google-ai-edge/LiteRT/commit/919670238240581ca8612ac5885b6b5b11b306ed)

#### LiteRT-LM 的 EmbeddingEngine 继续补齐端侧检索能力

`LiteRT-LM` `CLIP / 相册搜索`

**更新：** LiteRT-LM 在过去 24 小时继续完善 EmbeddingEngine：为 embedding LiteRT executor 设置 CPU / GPU options，`ComputeEmbedding` 新增输入溢出策略；同一窗口内还补充了 Embedding metadata、BOS/EOS token 信息和视觉预处理初始化等能力。

**意义：** 这不是单纯 LLM chat 路径的改动，而是在把 LiteRT-LM 的 embedding 能力做得更像可实际集成的端侧检索 runtime。对本地语义搜索、图文检索和相册搜索，设备选择、输入截断/溢出策略与视觉预处理都是工程上必须明确的环节。

**端侧判断：** 这些能力已经进入主分支，但不是独立正式 Release。值得继续观察其是否在下一版 LiteRT-LM 中形成稳定 API，以及是否出现 Android 上的 embedding / CLIP 真机 benchmark。

**来源：** [CPU / GPU options](https://github.com/google-ai-edge/LiteRT-LM/commit/a719d96fea15f4dc03e85a4df538eba34e757b25) · [Embedding input overflow](https://github.com/google-ai-edge/LiteRT-LM/commit/f11bba7acdbef8c671e7adbf300b7be0b012032d) · [Embedding metadata](https://github.com/google-ai-edge/LiteRT-LM/commit/a6f7effa3506cdef175a8def7008ee8b6b961ec3) · [Vision preprocessing](https://github.com/google-ai-edge/LiteRT-LM/commit/4d27740e0be2063fa28cfc94b4134b777c213780)

### MNN

#### DFlash 复用目标模型 LM Head，Qwen3-4B Int4 可少占约 219 MB

`MNN` `量化 / 模型优化`

**更新：** MNN 的 DFlash 草稿模型不再保存与目标模型重复的 `lm_head`，而是直接复用目标模型的 LM Head。官方提交给出的 Qwen3-4B Int4 示例可减少约 **219 MB** 磁盘与运行时重复权重；M5 iPad、2B Int4、batch 8、greedy 验证中 acceptance 从 4.59 到 4.63，基本保持一致。

**意义：** 对端侧 speculative decoding，数百 MB 的 ROM / RAM 节省往往比几个百分点的 kernel 提速更能决定模型能否落地。该改动针对的是明确的重复权重，而不是依赖降低精度换空间。

**端侧判断：** 已有 iPad 实测验证，但这是 MNN 主分支能力而非新正式 Release；旧 DFlash 导出物还需要按新配置重新导出，不能直接假定兼容。

**来源：** [MNN 官方 commit](https://github.com/alibaba/MNN/commit/bc85588f29e42b521dcff8a7a573c6423d7e09ad)

#### MNN 新增 Qwen3-TTS-12Hz-0.6B-Base 支持

`MNN` `Audio`

**更新：** MNN 主分支新增对 `Qwen3-TTS-12Hz-0.6B-Base` 的支持。这里的新变化是 **MNN runtime 适配**，不是 Qwen3-TTS 模型本身在今天新发布。

**意义：** 0.6B 级 TTS 是明显值得关注的端侧语音模型尺寸，MNN 接入使其从“理论上可压缩部署”进一步进入实际移动 runtime 生态，后续有机会形成离线 TTS / voice cloning 的手机端路径。

**端侧判断：** 当前不能仅凭“已支持”就视为成熟 Android 方案；仍应继续看量化位宽、峰值 RAM、首包延迟、实时率 RTF、音频 codec / decoder 开销和 Android 真机数据。若做手机部署，优先关注 Int4 / 混合精度路径。

**来源：** [MNN 官方 commit](https://github.com/alibaba/MNN/commit/becf43ef3d207206a6883c9dfca380c347defc95) · [Qwen 官方模型卡](https://huggingface.co/Qwen/Qwen3-TTS-12Hz-0.6B-Base)

#### MNN 修复 LLM 与 Visual 模型导入同一 QNN 目录

`MNN` `Qualcomm QNN`

**更新：** MNN 修复 QNN 转换流程，使 LLM 与 visual MNN 模型可以转换到同一个 QNN 输出目录，减少多组件模型导出时的目录冲突和产物组织问题。

**意义：** 对 Qwen-VL 一类语言模型与视觉组件组合的端侧 VLM，这类修复直接贴近真实 QNN 工程链路，比单独的桌面算子支持更有部署价值。

**端侧判断：** 这是 QNN 导出链路修复，不等同于某个 VLM 已在特定 Snapdragon SoC 上完整跑通；仍需结合模型支持列表、QNN 算子覆盖和目标 HTP 版本验证。

**来源：** [MNN 官方 commit](https://github.com/alibaba/MNN/commit/e24ef7c0acef2ffb02fbda452360b3a9197a855d)

#### llama.cpp Vulkan 首次加入 TQ2_0 ternary 支持

`llama.cpp` `量化 / 模型优化`

**更新：** llama.cpp 的 Vulkan backend 加入 **TQ2_0 ternary** 支持，包括 dequant、专用 `mul_mat_vec` 和 matmul 路径。官方提交说明，OM-125m TQ2_0 全量 offload 时 top-12 logprobs 与 F16 可一致到 4 位小数；125M 尺寸上速度约等于 F16，当前收益重点指向更大的 BitNet 类模型，MMQ / int-dot 路径尚未接入。

**意义：** 这是 ggml Vulkan 首个 ternary 类型支持，意味着极低比特 / ternary 模型开始获得更现实的跨 GPU runtime 路径。对移动 GPU 而言，潜在价值主要来自带宽和模型体积，而不是当前 125M microbenchmark 的速度。

**端侧判断：** 已有 Vulkan backend 支持，但不能直接等同于 Android Snapdragon 上已获得性能收益；需要后续 Adreno 真机 benchmark，并观察 MMQ / int-dot 是否补齐。

**来源：** [llama.cpp 官方 commit](https://github.com/ggml-org/llama.cpp/commit/a7cd2f0e98ffa4e939276287be1fa76891908d2e)

#### AArch64 / KleidiAI 增加运行时 CPU 特性检测

`llama.cpp` `ARM`

**更新：** llama.cpp 为 AArch64 / KleidiAI 增加 runtime feature detection，可在运行时判断 ARM CPU 特性，而不是完全依赖编译时假设。

**意义：** Android / ARM 设备的 ISA 能力差异较大，运行时检测有助于同一二进制更安全地选择优化路径，也能降低因目标设备缺少特定指令而产生的兼容性风险。

**端侧判断：** 这是通用 ARM CPU 路径改进，不是 QNN / HTP NPU 加速；对 CPU fallback 与跨设备分发更直接有价值。

**来源：** [llama.cpp 官方 commit](https://github.com/ggml-org/llama.cpp/commit/132753bf4e52b1a8bda8f6ec33f1785bd80470da)

## AI点评

- **LiteRT 的重点正在从“能否调用 accelerator”走向“能否验证真正完整 offload”。** 新增 accelerator query 和非 CPU 全加速查询后，端侧性能排障会更可观测，这对 NPU / GPU 转换链路很重要。
- **LiteRT-LM 的 EmbeddingEngine 值得持续跟踪。** CPU/GPU 选项、输入溢出、metadata 与视觉预处理逐步补齐后，它开始具备承载本地相册语义搜索/图文 embedding pipeline 的工程形态；下一步关键是 Android 真机模型与 benchmark。
- **MNN 今天的更新质量很高。** DFlash 直接省约 219 MB、Qwen3-TTS 0.6B 获 runtime 支持、QNN 多组件导出修复，三项都比普通 API 改名更接近真实手机部署问题。
- **极低比特正在向 GPU backend 扩散。** llama.cpp 把 TQ2_0 带到 Vulkan 是方向性信号，但当前仍缺 Adreno 等移动 GPU 的明确收益数据；后续是否补齐 int-dot / MMQ 会决定实际价值。
- **Android API 24 门槛需要提前留意。** LiteRT 主分支已经上调 minSdkVersion，虽然尚未形成新稳定 Release，但下一次升级依赖时应把兼容性检查列为必测项。
