## 模型与多模态

### LFM2.5-230M 新增 LiteRT-LM 端侧包：SM8850 GPU decode 约 122 tok/s
`LiteRT-LM` `Small LLM`

**更新：** LiteRT Community 新发布 `LFM2.5-230M` 的 `.litertlm` 转换，提供 266 MB int8 与 177 MB int4 两个 bundle。Galaxy S26 / Snapdragon SM8850 上两者均实现 OpenCL 全图 delegation（prefill/decode 均 492/492 nodes、0 rejected op）；其中 int8 GPU 实测 prefill 3813–3815 tok/s、decode 121.7–121.9 tok/s、峰值 RSS 444 MB，明显优于该机上的 int4 GPU decode 41.6–43.6 tok/s。

**判断：** 230M 级模型在手机上已经进入“几百 MB、百 tok/s decode”的实用区间，适合数据抽取、轻量 tool/agent pipeline；但这里是 **Adreno/OpenCL GPU**，不是 QNN/HTP NPU。对 SM8850 来说 int8 反而比 int4 更快，也说明小模型不能默认“量化越低比特越快”。

**来源：** [LiteRT Community / LFM2.5-230M](https://huggingface.co/litert-community/LFM2.5-230M)

## 音频、翻译与检索

### Granite Speech 5.0 470M 新增 LiteRT ASR：Galaxy S26 CPU 约 45× 实时
`ASR` `LiteRT`

**更新：** LiteRT Community 新发布 IBM Granite Speech 5.0 TurboCTC 470M 的 LiteRT 转换，int8 文件 518 MB、fp16 994 MB；Galaxy S26 上 int8 CPU 对 5/10/30 秒固定窗口的中位延迟分别为 106.4 / 220.2 / 666.4 ms，约 45× 实时。20 条 LibriSpeech dev-clean 小样本中 int8/fp16 转写均与 fp32 reference 20/20 一致；移动 GPU 当前因 `GATHER_ND` 无法编译该图。

**判断：** 这是一个很具体的端侧英文 ASR 新候选：CTC 无 autoregressive decoder/KV cache，CPU 已足够快；但 518 MB 仍偏大，而且当前既没有 GPU 路径，也没有 Snapdragon NPU/QNN/HTP 证据，不能把“45× real-time”理解成 NPU 加速。

**来源：** [LiteRT Community / granite-speech-5.0-470m-turboctc](https://huggingface.co/litert-community/granite-speech-5.0-470m-turboctc)

### mxbai-edge-colbert 32M 新增 LiteRT：39 MB late-interaction 检索模型
`Retrieval` `LiteRT`

**更新：** LiteRT Community 新发布 `mxbai-edge-colbert-v0-32m` 的 `.tflite` 转换：32M ModernBERT backbone，每个 token 输出 64 维单位向量，通过 MaxSim 做 late-interaction retrieval。推荐 int8 版本仅 39 MB、峰值 RSS 144 MiB；NanoSciFact 上 nDCG@10 为 0.8564（PyTorch 0.8644），Recall@5 与 Hit@1 均保持不变；服务端 PyTorch 建库、端侧 int8 query 的交叉版本检索同样基本保持排序质量。

**判断：** 对端侧相册/语义检索尤其值得测试：它不是单向量 embedding，而是用更高索引成本换更好的细粒度匹配；39 MB 模型体积很漂亮，但文档侧是多向量索引，必须把索引体积、MaxSim 延迟和中文效果一起评估，不能只看模型包大小。

**来源：** [LiteRT Community / mxbai-edge-colbert-v0-32m](https://huggingface.co/litert-community/mxbai-edge-colbert-v0-32m)

## AI点评

1. **今天最值得端侧关注的是 LFM2.5-230M。** SM8850 上 int8 GPU decode 约 122 tok/s、峰值 RSS 444 MB，已经接近“可以随手塞进产品做轻任务”的量级；下一步应优先看同尺寸中文/工具调用实测，以及是否能进入 QNN/HTP。
2. **低比特不等于更快。** LFM2.5-230M 在 Galaxy S26 上 int8 GPU decode 是 int4 的约 2.8×，说明 200M 级小模型里 dequant / kernel overhead 足以反转常见直觉；端侧量化选择必须以真机 profiling 为准。
3. **检索侧出现了比单向量 embedding 更值得试的新路线。** 39 MB ColBERT 转换把 late interaction 带到 LiteRT，但真正的成本会从“模型 RAM”转移到“文档多向量索引 + MaxSim”；适合用真实相册 query 做一个与 CN-CLIP / embedding 路线并行的小评测。
4. **ASR 端侧优化未必一定要追 NPU。** Granite Speech 470M 的 CPU 已达到约 45× real-time，说明 CTC 这类结构在端侧可以先用简单 runtime 跑到可用；是否值得继续做 GPU/NPU，应该看功耗、包体与并发需求，而不是只看 latency。
5. **行业侧越来越明显地把“能力、成本、权限”一起产品化。** Fable/Mythos 用同一底层模型切不同 safeguard envelope，Astra 则在 release 前先公开 Critical capability 与访问限制；frontier model 的发布正在从单纯模型版本升级变成 capability-governance 事件。
