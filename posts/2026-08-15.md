## 端侧框架与运行时

### LiteRT / LiteRT-LM

#### LiteRT-LM Embedding layer 开始直接接收 PCM 音频

`LiteRT-LM` `Audio`

**更新：** LiteRT-LM 主线新增对 **PCM audio data** 直接进入 Embedding layer 的支持；同一窗口还增加了 NPU runtime 的可选同步执行模式，并修复 Kotlin `suppressTokens` 跨 JNI 时因方法查找与名称修饰导致的问题。

**判断：** PCM 直接进入 embedding 层意味着 LiteRT-LM 的 pipeline 不再只围绕文本/视觉输入组织，音频前处理与多模态编排的接口正在往运行时内部收拢。NPU 同步执行则更偏工程可控性，适合调试、串行 pipeline 或需要明确执行边界的端侧场景。

**来源：** [PCM audio embedding commit](https://github.com/google-ai-edge/LiteRT-LM/commit/b4fbc38277b6e1733568660f1e7590f858851fc7)；[NPU synchronous execution commit](https://github.com/google-ai-edge/LiteRT-LM/commit/bd9754ea7d58af44eaf4f86bd84c596fa10bd4ac)；[Kotlin suppressTokens JNI fix](https://github.com/google-ai-edge/LiteRT-LM/commit/d9f242b4e548205601911bfe271a6f01d7b5752b)

#### LiteRT Rust/C++ API 继续补齐动态输入尺寸能力

`LiteRT` `API`

**更新：** LiteRT 主线将 Rust binding 对齐到 C++ API 2.2.0，并加入 `TensorBuffer::dimensions()` 与 `CompiledModel::resize_input_tensor_buffer()`，使动态输入 tensor 的尺寸读取与调整更直接。

**判断：** 这不是新的正式 Release，而是 2.2.0 之后的普通 commit。对动态分辨率视觉模型、可变长度输入和跨语言 binding 有实际价值，但短期影响低于 NPU/量化类性能更新。

**来源：** [LiteRT API commit](https://github.com/google-ai-edge/LiteRT/commit/68627c1f7190ed1636c8006707d7d88456cb571a)

### MNN

#### 修复 Qwen2.5-Omni Token2Wav 在 OpenCL 上的崩溃

`MNN` `Qwen2.5-Omni`

**更新：** MNN 合入针对 **Qwen2.5-Omni token2wav OpenCL crash** 的修复，对应公开 issue #4673；同时修复关闭 vision/audio 支持时的 LLM 构建问题。

**判断：** 这是直接影响端侧语音生成链路稳定性的修复。对于以 GPU/OpenCL 跑 Omni 音频输出的 Android 设备，比一般算子优化更值得优先回归，因为它处理的是“能否稳定运行”而不是小幅性能差异。

**来源：** [Qwen2.5-Omni OpenCL crash fix](https://github.com/alibaba/MNN/commit/1d392954e9a293922e9daa6396ab2274bd0f5e6f)；[LLM build fix](https://github.com/alibaba/MNN/commit/19af6dab54a8a238c1e684bf5a9584f1f283f5cc)

#### Metal 为 speculative-block decode 增加 Fused-Q4 M8 与 K-split

`MNN` `Metal`

**更新：** MNN Metal 后端为 speculative-block decode 增加专门的 **Fused-Q4 M8 tile** 与 **K-split** 路径，目标是解决 8-row speculative block 在原 M32 tile 下 occupancy 低、输出 tile 少时带宽利用不足的问题；新路径只在 speculative decoding 条件下启用。

**判断：** 这属于非常明确的低比特 decode 性能优化，尤其针对 Apple GPU。相比“支持某个量化格式”，它已经针对实际 speculative decoding 的矩阵形状做 kernel 级优化，后续值得关注真机 tok/s 与能效数据。

**来源：** [MNN Metal speculative Q4 optimization](https://github.com/alibaba/MNN/commit/fe05d704fde6dbe419b93c7798a11fd8cfd2e85b)

### Qualcomm Genie / GenieX / QNN / HTP

#### GenieX 修正 llama.cpp `swa_full` 默认值，并补 Gemma 4 tool-call 解析

`GenieX` `llama.cpp`

**更新：** GenieX 将 SDK 中 llama.cpp 的 `swa_full` 默认值修正为 `false`，并在 OpenAI-compatible server 侧加入 Gemma 4 tool-call 格式解析。

**判断：** `swa_full` 修正更值得端侧关注，因为 sliding-window attention 的错误默认配置可能直接改变内存占用与运行行为；Gemma 4 tool-call 则主要提升本地 Agent/server 的兼容性。两项均为普通主线 commit，不是新 Release。

**来源：** [swa_full default fix](https://github.com/qualcomm/GenieX/commit/a566136deff0e43db2bb57024d6c6af0f6b8f582)；[Gemma 4 tool-call support](https://github.com/qualcomm/GenieX/commit/92aba0367d9075ba8da0b6c4fe5ff699183ab99d)

## 模型与多模态

### 小模型 / 手机可部署模型

#### Qwen3-4B-Thinking-2507 发布 LiteRT-LM Int4 成品包

`Qwen3` `LiteRT-LM`

**更新：** LiteRT Community 在本窗口发布 `Qwen3-4B-Thinking-2507` 的 `.litertlm` 包，采用 blockwise-128 Int4 + OCTAV、INT8 embedding、4096 KV cache，文件约 **2.3–2.5 GB**。模型卡给出 iPhone 17 Pro GPU decode 约 **14 tok/s**，GSM8K 100 题从 bf16 的 90% 到 LiteRT Int4 的 86%。

**判断：** 这是“已有实际移动 runtime 适配”的 4B reasoning 模型，不只是理论可量化。2.5 GB 左右模型体积对高内存手机已经现实，但 thinking 模式需要较长输出预算，实际峰值内存和耗电仍应单独评估。

**来源：** [litert-community/Qwen3-4B-Thinking-2507](https://huggingface.co/litert-community/Qwen3-4B-Thinking-2507)；[LiteRT Community Activity](https://huggingface.co/organizations/litert-community/activity/all)

#### LiteRT Community 密集补齐真正“手机级”的视觉模型

`LiteRT` `Vision`

**更新：** 本窗口新发布多款已做 Android 真机验证的 LiteRT 视觉模型：M-LSD-tiny 仅 **1.4 MB fp16**、Pixel 8a GPU 约 **2 ms**；Places365 ResNet18 **22.8 MB fp16**、约 **2 ms**；RTMPose-s 约 **11.1 MB**、约 **4 ms**；RTMPose-Hand **28 MB**、约 **4 ms**；RTMW-m WholeBody **66 MB**、约 **6 ms**。这些模型卡均标注 Pixel 8a / Tensor G3 上 GPU 全量 delegate。

**判断：** 这批模型虽然没有 LLM 那么吸睛，但更接近真实手机功能模块：场景识别、直线检测、人体/手部/全身关键点都能做到毫秒级且模型体积很小。对相册、相机、姿态交互类产品，其工程价值往往高于大模型 demo。

**来源：** [LiteRT Community Activity](https://huggingface.co/organizations/litert-community/activity/all)；[M-LSD-tiny-LiteRT](https://huggingface.co/litert-community/M-LSD-tiny-LiteRT)；[Places365-ResNet18-LiteRT](https://huggingface.co/litert-community/Places365-ResNet18-LiteRT)；[RTMPose-s-LiteRT](https://huggingface.co/litert-community/RTMPose-s-LiteRT)；[RTMPose-Hand-LiteRT](https://huggingface.co/litert-community/RTMPose-Hand-LiteRT)；[RTMW-m-WholeBody-LiteRT](https://huggingface.co/litert-community/RTMW-m-WholeBody-LiteRT)

## AI点评

- **LiteRT-LM 的边界正在从“LLM runtime”继续外扩。** PCM audio 进入 embedding layer 与此前 embedding engine 的演进放在一起看，统一多模态 pipeline 的轮廓越来越清晰。
- **端侧模型生态开始出现“两极同时成熟”的趋势。** 一边是 4B Int4 reasoning 模型能在 iPhone 上达到十几 tok/s，另一边是 1–60 MB 的经典视觉网络在 Android GPU 上做到 2–6 ms；真正产品化时两类能力可以互补，而不是互相替代。
- **MNN 这期更偏“可用性 + kernel 级性能”。** Qwen2.5-Omni OpenCL crash 属于必须修的稳定性问题，Metal Fused-Q4 则直接针对 speculative decode 的真实矩阵形状，后续真机数据值得重点跟踪。
- **GenieX 本期没有新的版本号，但配置默认值修复不应忽略。** 对 sliding-window attention 一类机制，默认参数错误可能比一次普通性能优化更容易造成内存与行为异常。
